## 1. `--cli`: acción directa sin modelo

`python mcp_server.py --cli <herramienta> [json-args]` — herramientas: `gui_attach`, `gui_status`, `server_stop`, `server_status`, `cancel`.
No importa `mcp` (arranca en ~0,15 s). Escribe UNA línea JSON UTF-8 por stdout (la última línea de stdout). Medido contra el solver falso:
server_status 0,21 s, gui_status 0,18 s, cancel 0,15 s; sin servidor (estado real) 0,1 s.

| ejemplo | resultado |
|---|---|
| `--cli server_status` | `{"alive": true, "idle_min": 0.0, "turno": null, "pid": …, "pid_real": …, "port": …, "sim": …, "gui": false, "gui_pids": [], "ms": 106, "via": "ninguno", …}` |
| `--cli gui_status` | `{"connected": false, "pids": [], "port": 47827, "server_alive": true, "ms": 20}` |
| `--cli gui_attach '{"wait_s": 0}'` | `{"ok": true, "launched": 1234, "connected": false, "pids": [], "note": "…"}` (con GUI ya abierta: `{"ok": true, "already": true, …}`; sin servidor: `{"ok": false, "error": "…"}`) |
| `--cli server_stop '{"save": true}'` | `{"stopped": true, "saved": "…sim", "residente": "detenido", "gui_warning": "…"?, "timings_s": {"guardar": 0.1, "apagar": 0.3, "residente": 0.0, "total": 0.4}, "ms": …}` |
| `--cli cancel '{"wait_s": 15}'` | ver §3 |

- Código de salida: 0 si la herramienta respondió (aunque diga `ok:false`/`stopped:false`), 1 si lanzó una excepción (`{"ok": false, "error": "…"}`), 2 si el uso es
  incorrecto (herramienta desconocida o JSON roto; `{"ok": false, "error": "uso: --cli <…> [json-args]"}`).
- **Candado de turnos**: `server_stop` toma el turno como siempre pero espera como mucho `COPILOTO_CLI_LOCK_WAIT_S` (3 s, no los 120 s de las tools del MCP). Si otro proceso
  itera: `{"stopped": false, "busy": "el solver lo usa «iterate» (pid N) desde hace 12 s; reintenta luego", "holder": {…}}` y exit 0. `gui_*`, `server_status` y `cancel` no toman el turno
  (`cancel` es, por diseño, lo único que actúa mientras otro lo tiene).
- Argumentos extra a `server_stop` (`save`), `gui_attach` (`wait_s`), `cancel` (`wait_s`); un nombre de argumento desconocido da código 2.
- `server_stop` desde el CLI es lo que tarde el guardado (el residente lo inyecta como siempre). El resultado trae `timings_s` por fase.

## 2. `progreso.json` (progreso en vivo)

Ruta: `estado_dir()/progreso.json` (= `panel_estado.json["estado_dir"]` + `/progreso.json`). Lo escribe un hilo del proceso que itera (iterate o pump_case,
también cuando pump_case llama a iterate) cada **1,0 s** (`PROG_EVERY_S`), de forma atómica (tmp + replace), leyendo el `.out` de la macro en curso: marcadores `PIPE <fase> <s>`,
`ITER\t<it>\tH <v>\tM <v>`, `ITER_STOP`, `ITERATION n` + `REPORT\tH\tv` (iterate) y la **tabla de monitores del solver** (cabecera `Iteration Continuity … M (N-m) H`, una fila por
iteración, así que H, M y continuidad avanzan iteración a iteración, no por bloque). NaN/Infinity salen como `null` (JSON válido).

```json
{
 "schema": 1,
 "tool": "pump_case",                     // "pump_case" | "iterate"
 "caso": "BombaRapida",                   // pump_case: el caso; iterate: stem del .sim
 "fase": "iterar",                        // arrancar | importar | regiones | fisica | mrf | fronteras | reportes | mallar | euler | iterar | post | terminado
 "fases_s": {"importar": 7.97, "regiones": 0.25, "fisica": 1.29, "mrf": 0.19, "fronteras": 0.17, "reportes": 0.98, "malla": 50.17, "euler": 0.96},  // fases ya terminadas (de los PIPE)
 "iteracion": 150, "iter_max": 1000, "criterio": "stable",   // criterio: "stable" | "n"
 "H": 16.7439, "M": 8.4570, "eta": 0.8864, "continuidad": 0.001454,   // últimos valores; null si no existen aún
 "variacion_pct": 7.859,                  // (máx−mín)/media de H y M en la ventana (100 it) — lo que juzga «stable»; null si aún no hay ventana
 "ritmo_it_s": 2.483,                     // iteraciones por segundo (null hasta tener dos lecturas)
 "inicio": "2026-10-26T18:44:34", "transcurrido_s": 187.4,
 "falta_s": 160.0,                        // ESTIMACIÓN de lo que falta, s (ver abajo); null si no se puede
 "falta_max_s": 342.3,                    // cota superior: lo que tardaría si llega a iter_max; solo en fase iterar
 "falta_its": 397,                        // iteraciones estimadas que faltan (fase iterar)
 "falta_fuente": "ritmo",                 // "ritmo" (iterar) | "referencia" (fases anteriores, de la última corrida) | null
 "cancelando": false,                     // true desde que se vio un cancel()
 "terminado": false,
 "resultado": null,                       // al terminar: ver abajo
 "actualizado": "2026-10-26T18:47:42", "t": 1793058274.17,   // t = epoch del último latido
 "pid": 20776                             // pid del proceso que escribe (el MCP que itera)
}
```

- **Terminado**: `fase: "terminado"`, `terminado: true`, `falta_s: 0.0`, `resultado` = `{"ok", "stopped", "iterations_run", "iteration", "seconds", "cancelled"?, "error"?, "exception"?, "busy"?, "failed_at"?}`
  y, si hay, `iterate: {ok, stopped, iterations_run, iteration, reports, variation_pct}` y `RESULT: {H, M, eta, …}` (de `parsed`). Si la tool lanzó: `resultado = {"ok": false, "error": "…"}`.
  Se escribe también cuando acaba por cancelación (`resultado.cancelled: true`, `resultado.stopped: "cancelled"`).
- **Cómo lee el panel**: viva si `terminado == false` y `time.time() - t < 10` y el `pid` existe. Si `terminado == false` pero el latido tiene > 10 s o el pid murió (Detener mató al
  MCP), la corrida está muerta: mostrar «interrumpida» (el archivo no se corrige solo). Cada corrida nueva reescribe el archivo entero.
- **Estimación de `falta_s`**: en iterar, `restantes / ritmo`, con `restantes` = llenar la ventana (100 it) + ~½ ventana si aún no hay ventana completa; si la variación ya es ≤ tol, ~¼ de
  ventana; si no, `ventana · ln(tol/v) / ln(r)` con `r` = cociente entre la variación de esta ventana y la anterior (0,05–0,95; ½ si no hay dato), siempre acotado por lo que queda hasta `iter_max`.
  Antes de iterar usa lo que tardó cada fase en la última corrida (`estado_dir()/fases_ref.json`, lo guarda pump_case al terminar). Es una guía, no una promesa.
- `falta_max_s` + `iter_max` dan la barra «hasta N iteraciones»; `variacion_pct` frente a 0,5 % da «cuánto falta para estable».

## 3. `cancel()` (tool MCP y `--cli cancel`)

Doc de STAR-CCM+ (`doc\en\online\STARCCMP`, «Setting a Stop File»): el criterio **Stop File** vigila un archivo `ABORT` (ruta por defecto relativa al directorio de trabajo del
servidor; en Windows basta un archivo vacío) y detiene el solver. Aquí: `abort_file()` = `sims/ABORT` (el servidor se lanza con `cwd=sims/`) y cada bloque de `iterate` (y el init de
`server_start`) deja el criterio activo con la ruta absoluta (`AbortFileStoppingCriterion.setAbortFilePath/setIsUsed`, a prueba de fallos; compila con el javac real).

Flujo: `cancel()` lee `progreso.json`; solo actúa si hay iteración en curso (fase `iterar`, latido < 10 s, dueño vivo). Entonces escribe `cancel.json` (`{t, by, kill, iteracion, tool}`),
crea `sims/ABORT` y espera hasta `wait_s` (15) a que el dueño termine. El dueño (iterate/pump_case):
- ve `cancel.json` (posterior al inicio de su tool) entre bloques y mientras espera al residente; el bloque en curso para solo por el ABORT, la tool devuelve `stopped:"cancelled"`, `cancelled:true`,
  con `iterations_run` e `iteration` reales (la solución llega hasta la última iteración);
- si la macro no acaba sola en `COPILOTO_CANCEL_GRACE_S` (8 s) — el caso de la macro de `pump_case` con `iterar:true`, donde el bucle del pipeline volvería a pedir bloques —, la abandona: mata el residente
  (nunca el servidor), lo relanza sin esperar su latido y devuelve `cancelled:true` (el post-proceso de esa macro se pierde; se repite aparte);
- borra `ABORT` y `cancel.json` al terminar (si no hay dueño, lo hace `cancel`). Un `ABORT` viejo se borra al empezar cualquier corrida (si no, pararía al instante).
- Respaldo: si tras 5 s el ABORT no detuvo nada (la iteración sigue avanzando), `cancel` lanza un cliente batch aparte con `sim.getSimulationIterator().stop()` (`metodo: "ABORT+stop()"`).

Resultado (`--cli cancel` y tool): `{"ok": true, "cancelled": true, "iteracion_en_curso": true, "iteracion": 480, "metodo": "ABORT", "turno": null, "segundos": 0.2, "abort_pendiente": false}`.
Sin iteración en curso (no crea ABORT; no toca nada): `{"ok": true, "cancelled": false, "iteracion_en_curso": false, "fase": "mallar"|null, "turno": {…}|null, "reason": "no hay iteración en curso (la macro está en la fase «mallar»: no se interrumpe; usa server_stop)"}`.
Sin servidor: `{"ok": true, "cancelled": false, "iteracion_en_curso": false, "reason": "no hay servidor vivo"}`. Si no paró en `wait_s`: `cancelled: false` + `reason` (el dueño lo borrará al acabar).
**No** cancela mallado, importar ni macros de `run_java`/`run_steps` (matar el residente a mitad de una malla deja el .sim a medias): para eso `server_stop`.

## 4. Pids reales y vigilante

`.server.json` ahora trae (el vigilante los refresca en cada chequeo, cada 30 s, y `server_start` el primero):

| clave | qué es |
|---|---|
| `pid` | pid del lanzador del servidor (el `.bat`; sirve para `taskkill /T`, como hasta ahora; el panel protege este) |
| `pid_real` | el proceso REAL: descendiente más profundo de `pid` con `-server` en su línea de comandos (`_real_pid`, vía snapshot + PEB) |
| `vigilante` | pid REAL del vigilante (él mismo se lo escribe; antes se logueaba el del redirector del venv, 25436 frente a 25228) |
| `residente`, `residente_real` | pid del residente vivo de ESTE servidor (el de `residente.json`) y el proceso real (`Residente.java`) |
| `gui`, `idle_min`, `idle_warning`, `idle_checked` | como antes; `idle_checked` (ISO) se escribe en CADA chequeo; el panel debe avisar «sin vigilante» si pasa > 2 min |

`_vigilante_ensure` espera (≤ 3 s) al archivo `vigilante-<puerto>.json` y devuelve/loguea ese pid, no el del lanzador (`vigilante lanzado pid 25228 (…, lanzador 25436)`).
